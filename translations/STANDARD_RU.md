# Стандарт качества архитектуры памяти ассистента

**Формат:** чек-лист для аудита — разместить перед собой и сверяться по пунктам.
**Версия:** 1.2 (2026-08-27)
**Область применения:** любые LLM-ассистенты и агенты с долговременной памятью (диалоговой, эпизодической, семантической, векторной, графовой, мультимодальной), независимо от стека и платформы.

---

## Глоссарий

| Термин | Определение |
|--------|-----------|
| **Хранилище (Store)** | Любой слой персистентности для данных памяти: SQLite база, векторный индекс, JSON файл, RAM-кэш, граф |
| **Происхождение (Provenance)** | Запись о происхождении элемента памяти: кто создал, когда, из какого источника, в какой сессии |
| **Контаминация обратной связи (Feedback contamination)** | Когда сгенерированный моделью вывод сохраняется как память и позже извлекается так, будто это внешний ввод, создавая самоподкрепляющуюся петлю |
| **Живая память (Alive memory)** | Запись памяти, защищённая от суммаризации и decay из-за эмоциональной или культурной значимости; ограничена потолком количества |
| **Слепая обрезка (Blind truncation)** | Обрезка текста по лимиту символов/токенов (`text[:limit]`) без учёта семантических границ; запрещена стандартом |
| **Bare-вызов** | Вызов API суммаризации/компрессии без передачи истории диалога и без записи результата обратно в память |
| **Decay (затухание)** | Постепенное снижение importance-скора записи памяти со временем, обычно экспоненциальное (кривая Эббингауза) |
| **Мост (Bridge)** | Контролируемая точка инъекции между двумя изолированными хранилищами; единственный разрешённый путь кросс-хранилищного обмена |
| **Хранитель (Guardian)** | Системный оркестратор, отвечающий за запуск, остановку, мониторинг и диагностику всех процессов ассистентов |

## 1. Базовая модель контура

Аудит ведётся относительно обобщённого контура памяти. Каждый пункт чек-листа привязан к узлу или ребру этой модели.

```
ВХОД (пользователь, файлы, web, изображения, другие агенты, внешние модели)
  → ПРИЁМ / INGESTION (валидация, извлечение смысла, оценка важности)
  → ХРАНЕНИЕ / STORAGE (сообщения, эпизоды, концепты, векторы, графы, кэши)
  → ВЫБОРКА / RETRIEVAL (релевантность, свежесть, важность, границы)
  → СБОРКА КОНТЕКСТА / ASSEMBLY (форматирование, сжатие, инъекции, бюджеты)
  → МОДЕЛЬ / LLM
  → ВЫХОД / OUTPUT (ответы, действия: файлы, поиск, вызовы памяти)
  → ОБРАТНАЯ СВЯЗЬ / FEEDBACK (выход возвращается в ПРИЁМ)   ← контур замкнут
```

Ключевое свойство контура — замкнутость: всё, что попало в память, возвращается модели и способно воспроизводиться. Большинство тяжёлых отказов памяти — это отказы рёбер, а не узлов.

### Контур → Секции (маппинг)

| Узел контура | Основные разделы | Что проверяется |
|--------------|-----------------|-----------------|
| ВХОД | A | Валидация, секреты, фильтр доверия |
| ПРИЁМ | A, B | Извлечение смысла, целостность записи |
| ХРАНЕНИЕ | B, C, G | Идемпотентность, рост, изоляция |
| ВЫБОРКА | D | Ранжирование, гейтинг, совместимость embeddings |
| СБОРКА | E | Суммаризация, бюджеты, позиционирование |
| МОДЕЛЬ/LLM | — | (Вне области стандарта) |
| ВЫХОД | E, I | Действия, команды, наблюдаемость |
| ОБРАТНАЯ СВЯЗЬ | F | Антирекурсия, предотвращение эха |
| Сквозные | H, I, J | Конкурентность, восстановление, управление изменениями |

## 2. Как проводить аудит

### 2.1. Подготовительная фаза (ОБЯЗАТЕЛЬНА для действующих систем)

Перед началом аудита по разделам 0–K необходимо подготовить систему. Пропуск подготовки — главная причина инцидентов при аудите (удаление живых данных, засорение памяти тестами, потеря взаимосвязей между хранилищами).

**Шаг П1. Бэкап всех данных.**
Полная копия всех БД, конфигов и состояния. Бэкап — до любых действий. Без бэкапа — не начинать.

**Шаг П2. Инвентаризация хранилищ и путей.**
Выявить ВСЕ БД файлы (включая дубли, старые версии, кэши в корне проекта). Для каждого: реальный путь, размер, дата изменения, какой код его использует. Не доверять именам — проверять через `grep` и трассировку кода. Если пути в коде расходятся с реальным расположением — зафиксировать, не исправлять до составления плана.

**Шаг П3. Сверка таблиц и взаимосвязей.**
Для каждой БД: полная схема (`sqlite_master`), количество записей, связи между таблицами (FK, общие ключи). Выявить: сиротские записи (vectors без messages, embeddings без source), дубли БД (одна и та же таблица в разных файлах), рассинхронизацию между хранилищами. Зафиксировать как есть.

**Шаг П4. Если расположение неправильное — миграция, не удаление.**
Дубли БД, файлы не в тех директориях, устаревшие версии — мигрировать, сливать, переносить. **Никогда не удалять при миграции** без предварительного анализа содержимого и подтверждения контролёра, за исключением случаев когда немедленное удаление требуется политикой безопасности, конфиденциальности или законодательством. Доиндексация, коррекция путей в коде, слияние таблиц — до начала аудита.

**Шаг П5. Проверка существующих тестов.**
Запустить все существующие тесты. Если есть красные — зафиксировать и классифицировать ДО аудита. Не считать существующие сбои свидетельством вновь внесённых дефектов. Известные сбои и новые находки аудита ведутся раздельно.

**Шаг П6. Изоляция тестирования.**
Убедиться что тестовая среда изолирована от продакшн-хранилищ: tempfile/in-memory БД, моки API. Тесты аудита **не должны** записывать данные в живую память, создавать записи в продакшн-таблицах или модифицировать состояние ассистента.

**Шаг П7. Проверка размера логов.**
Перед началом аудита проверить размер всех лог-файлов. Неконтролируемо разросшиеся логи (сотни MB) блокируют работу агента-аудитора и делают анализ невозможным. Для каждого лога свыше порога (например, 50MB): создать ротированную копию (`mv app.log app.log.YYYYMMDD`), создать пустой файл с тем же именем (`touch app.log`). Не удалять старые логи — они могут содержать доказательства инцидентов.

**Шаг П8. Осведомлённость об исполняемой среде.**
Перед началом аудита зафиксировать uptime системы и дату последних обновлений ОС/пакетов. Накопленное runtime-состояние (кэши процессов, обновлённые но не перезагруженные библиотеки, устаревший скомпилированный байткод) может маскировать или имитировать дефекты памяти. Если дефект исчезает после перезагрузки системы — это проблема исполняемой среды, не архитектуры памяти; фиксировать отдельно и не засчитывать против стандарта.

Только после выполнения шагов П1–П8 можно приступать к аудиту по разделам.

### 2.2. Проведение аудита

1. **Сначала раздел 0 (карта).** Без полной карты хранилищ результаты остальных разделов недостоверны.
2. Проходить разделы A–K по порядку. Каждый пункт помечать: `да` / `частично` / `нет` / `н/п` (неприменимо).
3. Для каждого `нет` и `частично` фиксировать **доказательство**: файл и строку, SQL-запрос с результатом, дамп, снимок промпта, лог. Утверждение без доказательства не считается проверенным.
4. Маркеры критичности:
   - **[КРИТ]** — прямой риск потери, отравления, утечки или неконтролируемого роста памяти. Провал = блокер.
   - **[ВАЖ]** — риск тихой деградации качества и предсказуемости.
   - **[РЕК]** — зрелость и сопровождаемость.
5. Вердикт (раздел «Протокол результата») выносить только по закрытой карте.

### 2.3. Реализация исправлений (роадмап)

По результатам аудита составляется роадмап — приоритизированный план исправлений. Реализация ведётся волнами (спринтами):

**Правило:** одно логическое изменение за интервал наблюдения (J1).

**После каждой волны — обязательно:**
1. Все тесты зелёные (старые + новые guard-тесты).
2. Коммит с описанием что именно исправлено.
3. Обновление статуса роадмапа (отметка выполненного + добавление новых пунктов если обнаружились «сюрпризы»).
4. Baseline-замер до/после (в записях, токенах, числах — не «на глаз»).

**Роадмап — живой документ:** в процессе реализации неизбежно обнаруживаются пункты, не учтённые в первоначальном плане. Они добавляются в роадмап с приоритетом и не реализуются вне очереди.

### 2.4. Диагностические скрипты старта и остановки

Завершающий этап аудита — проверка (или создание) диагностических скриптов:

**Стартовый скрипт** — при запуске системы проводит проверку всех компонентов:
- Доступность всех БД (каждая по отдельности)
- Доступность всех слоёв памяти (каждый независимо)
- Доступность внешних зависимостей (API, модели, порты)
- Целостность активного диалога (существует, восстановим)
- При ошибке: показать проблему, предложить решение, **не запускать** полуфункциональную систему

**Скрипт остановки** — мягкое завершение с сохранением состояния:
- SIGTERM (не SIGKILL)
- Запись последнего состояния диалога в БД
- Подтверждение что процесс завершён
- Информация для последующего восстановления

Диагностические скрипты должны быть **интегрированы в систему**, а не существовать как отдельные утилиты. Они — часть архитектуры, не дополнение к ней.

## Раздел 0. Карта системы (подготовка)

- [ ] **0.1** Составлена полная карта хранилищ: реляционные БД, файловые и векторные индексы, JSON-хранилища, кэши (RAM и дисковые), внешние источники данных. **[КРИТ]**
- [ ] **0.2** Для каждого хранилища определено, какие модули в него пишут и какие читают (владение чтение/запись). **[КРИТ]**
- [ ] **0.3** Определены все ключи доступа: по каким полям идёт запись и по каким — выборка; подтверждено, что ключ записи совпадает с ключом чтения. **[КРИТ]**
- [ ] **0.4** Выявлены все каналы, где выход модели (ответы, отчёты, результаты действий) возвращается на вход памяти. **[КРИТ]**
- [ ] **0.5** Сверено: анализируемый код совпадает с исполняемым (проверены импорты, активная реализация, нет «мёртвой» параллельной версии). **[КРИТ]**
- [ ] **0.5a** Каждая функция памяти, имеющая зелёные тесты, верифицирована на вызов из production pipeline. Зелёные тесты на код, который никогда не вызывается работающей системой — ложный сигнал безопасности. Проследить от точки входа теста до production call site; если production-вызывающего нет — функция мертва. **[КРИТ]**
- [ ] **0.6** Сняты baseline-метрики: объёмы хранилищ (записей/байт), размер типичного собранного контекста в токенах, время выборки. **[ВАЖ]**
- [ ] **0.7** Определены все точки, где пользовательский или внешний контент попадает в привилегированные (системные) части промпта. **[КРИТ]**

## Раздел A. Валидация входа (INGESTION)

- [ ] **A1** Все внешние источники (файлы из наблюдаемых директорий, web-контент, изображения, вывод других агентов) проходят фильтр доверия до записи в память. **[КРИТ]**
- [ ] **A2** Секреты (ключи, токены, пароли, персональные данные) детектируются и исключаются до индексации и векторизации. **[КРИТ]**
- [ ] **A3** Служебный контент (логи, диагностические отчёты, служебные маркеры, промпты) маркируется флагом и исключается из сборки контекста (при этом может оставаться в истории). **[КРИТ]**
- [ ] **A4** Извлечение смысла не совпадает с извлечением по форме: фрагменты кода, синтаксис, пути и технические маркеры не становятся «концептами»/«воспоминаниями». **[ВАЖ]**
- [ ] **A5** Для каждой записи фиксируется происхождение: источник, время, агент-автор, сессия. **[ВАЖ]**
- [ ] **A6** Записи из недоверенных источников получают понижающий вес или помещаются в отдельную зону доверия. **[ВАЖ]**
- [ ] **A7** Контент, встроенный во входы мультимодальных каналов (текст на изображении, метаданные файлов), проходит ту же валидацию, что и явный текст. **[КРИТ]**

## Раздел B. Идемпотентность и целостность записи (WRITE)

- [ ] **B1** Запись идемпотентна: повторная доставка события (retry, дублирование обновлений, двойной вызов) не создаёт дубликат — дедупликация на прикладном уровне или UNIQUE-ограничение в схеме. **[КРИТ]**
- [ ] **B2** Направление дедупликации корректно: сохраняется актуальная запись, гасится старый дубль (а не наоборот). **[КРИТ]**
- [ ] **B3** Дедупликация ведётся по смысловому/контентному ключу, а не по источнику. Семантически дублирующая информация из разных источников не создаёт нескольких активных записей в памяти. Разнообразие источников сохраняется как происхождение (provenance) или подтверждающее свидетельство, а не как дублированная память. **[ВАЖ]**
- [ ] **B4** Запись в несколько хранилищ (сообщение + вектор + индекс) транзакционна или компенсируема: исключены частичные записи («сообщение сохранено, вектор — нет»). **[ВАЖ]**
- [ ] **B5** Отказ записи не проходит молча: логируется, метрикуется, повторяется с backoff; «тихий return False» без наблюдаемости недопустим. **[КРИТ]**
- [ ] **B6** Сжатое представление (summary) и оригинал записываются согласованно; пустое/ошибочное сжатие не подменяет оригинал. **[КРИТ]**

## Раздел C. Управление ростом (GROWTH)

- [ ] **C1** Для каждого хранилища определены лимиты или политика retention (максимальный объём, глубина истории, поведение при переполнении). **[ВАЖ]**
- [ ] **C2** Повторная индексация/пересборка идемпотентна: повторный прогон не размножает записи. **[КРИТ]**
- [ ] **C3** Определены квоты: размер одной записи, число записей на сессию/источник, суммарный объём на контейнер. **[ВАЖ]**
- [ ] **C4** Векторный индекс синхронизирован с источником: удаление/гашение записи отражается в индексе; порядок операций (очистка источника → пересборка индекса) зафиксирован и соблюдается. **[КРИТ]**
- [ ] **C5** Кэши (RAM-структуры, кэши суммаризаций) имеют TTL или механизм инвалидации и включены в карту роста. **[ВАЖ]**
- [ ] **C6** Мониторится динамика объёмов; аномалии (кратный рост за одну операцию) алертятся. **[ВАЖ]**
- [ ] **C7** Дедупликация мультимодальных входов по хэшу не создаёт неограниченный рост счётчиков и не позволяет «затопить» свежесть памяти потоком уникальных вариантов. **[ВАЖ]**

## Раздел D. Ранжирование и гейтинг при выборке (RETRIEVAL)

- [ ] **D1** Статическая «важность» записи не компенсирует низкую релевантность: применяется контекстно-адаптивный скоринг (вес важности корректируется близостью к запросу) и мягкий порог релевантности, ниже которого запись не попадает в контекст даже при высокой важности. **[КРИТ]**
- [ ] **D2** Гейты-эвристики («разговорный запрос → минимум памяти») не отключают долговременную память целиком для легитимных запросов; условия гейта узкие и ревизуемые. **[КРИТ]**
- [ ] **D3** Эвристики важности устойчивы к накрутке: пользователь не может поднять ранг записи флудом, вопросительными знаками, ключевыми терминами или иными прозрачными приёмами. **[ВАЖ]**
- [ ] **D4** Recency-буст ограничен порогами: свежий нерелевантный контент не вытесняет старый релевантный. **[ВАЖ]**
- [ ] **D5** Выборка детерминирована между рестартами: ключи персистентны; недетерминированные хэши/идентификаторы не используются как ключи доступа. **[КРИТ]**
- [ ] **D6** Пороги, лимиты и веса выборки вынесены в конфигурацию, а не зашиты магическими числами в код. **[РЕК]**
- [ ] **D7** Управляемое извне гашение важности (архивация по внешнему контенту, перевод сессии в «решённое» по реплике пользователя) ограничено порогами, защитой свежих записей и текущей областью действия. **[КРИТ]**
- [ ] **D8** Embedding-модель соответствует языку(ам) данных. При смене embedding-модели версии embeddings явно отслеживаются и совместимость проверяется. Хранилища с несовместимыми embeddings переиндексируются или мигрируются до того как допускается смешанный поиск. **[КРИТ]**
- [ ] **D9** Результаты из внешних источников (web search, file read, RAG) фильтруются по активному семантическому контексту текущей сессии до сборки контекста. Совпадение по ключевым словам при нулевой концептуальной релевантности текущему диалогу помечается как низкорелевантное или исключается. Без этого фильтра запрос «Apple» при обсуждении программирования может принести рецепт яблочного пирога вместо ссылки на фреймворк. **[ВАЖ]**

## Раздел E. Сборка контекста (ASSEMBLY)

- [ ] **E1** Слепая обрезка семантически значимого контента запрещена: любое сокращение — суммаризация по смыслу; обрывки «посреди фраз» не попадают в промпт. Отбрасывание целых блоков с наименьшим приоритетом в рамках определённого бюджета токенов не является слепой обрезкой. **[КРИТ]**
- [ ] **E2** Полный оригинал хранится отдельно от сжатого представления (двухфазное хранение: оригинал — в истории, сжатие — в контекст). **[КРИТ]**
- [ ] **E3** Кэш сжатых представлений инвалидируется при изменении, восстановлении или переоценке исходников; TTL определён. **[ВАЖ]**
- [ ] **E4** Структурированные блоки (код, таблицы) не должны сжиматься способом, разрушающим их семантику; они сохраняются целиком или представляются через без-потерьную/валидированную альтернативу. **[ВАЖ]**
- [ ] **E5** Определены бюджеты на каждый инъектируемый блок (символы/токены), включая результаты инструментов и воспоминания. **[ВАЖ]**
- [ ] **E6** Пользовательский ввод не попадает в привилегированные блоки промпта (приоритеты, системные секции, заголовки памяти) без строгой валидации всех полей. **[КРИТ]**
- [ ] **E7** Доверенные маркеры (системные префиксы, маркеры инструментов, обозначения источников памяти) не могут быть имитированы пользовательским текстом — вход фильтруется от их форматов. **[КРИТ]**
- [ ] **E8** Шаблонные символы (`%`, `_`) и метасимволы в пользовательских запросах экранируются в LIKE/regex-поиске по памяти. **[ВАЖ]**
- [ ] **E9** Команды/действия, извлекаемые из текста ответа модели (файловые операции, поиск, вызовы памяти), валидируются: пути, разрешения, подтверждения, лимиты. **[КРИТ]**
- [ ] **E10** Определён механизм защиты эмоционально значимых записей от суммаризации и decay (защищённая/живая память); максимальное число защищённых записей ограничено потолком. **[РЕК]**
- [ ] **E11** Критически важная информация размещается в начале и конце контекстного окна, не в середине; для длинных контекстов, особенно где наблюдалось позиционное снижение внимания, это размещение проверяется (см. Liu et al., «Lost in the Middle», 2023). **[ВАЖ]**

## Раздел F. Контур обратной связи (FEEDBACK LOOP)

- [ ] **F1** Выход модели (ответы, отчёты, результаты действий) фильтруется перед возвратом в память: мета-контент («анализ анализа», служебные summaries, отчёты о самом контексте) не записывается как обычный контент. **[КРИТ]**
- [ ] **F2** Суммаризатор/компрессор не замыкает петлю обратной связи: вызов суммаризации не инициирует запись в память, не получает историю диалога и не возвращается в основной контур обратной связи. **[КРИТ]**
- [ ] **F3** Повторная суммаризация ограничена и отслеживает происхождение: summary не может молча становиться источником бесконечного дальнейшего сжатия. Максимальная глубина компрессии определена. **[ВАЖ]**
- [ ] **F4** Существует детектор рекурсивных артефактов: сигнатуры мета-ответов, контроль доли сгенерированного моделью контента в памяти, алерт при росте. **[ВАЖ]**
- [ ] **F5** Результаты вызовов памяти, вставляемые в текст ответа, не «протекают» обратно в долговременную память без фильтра. **[КРИТ]**
- [ ] **F6** Путь «ошибка входа → искажённый ответ → запись искажения в память» разорван: ошибки сборки контекста не маскируются под валидный контент. **[КРИТ]**

## Раздел G. Изоляция и границы доверия (ISOLATION)

- [ ] **G1** Границы изоляции не вырождены: граница должна демонстрируемо различать как минимум две независимо тестируемые области. Фильтр, который на практике всегда пропускает одно и то же значение (единый идентификатор области), — не граница, а её имитация. **[КРИТ]**
- [ ] **G2** Кросс-областной перенос возможен только через явный контролируемый канал (мост, маппинг, разрешённые ассоциации), а не через общий поиск. **[ВАЖ]**
- [ ] **G3** Fallback-ветки выборки не возвращают нерелевантный контент «лишь бы что-то»: пустой результат честнее случайного наполнения. **[ВАЖ]**
- [ ] **G4** Внешние хранилища (принадлежащие другим системам) подключены по контракту: изменение схемы/семантики внешней стороной детектируется, а не молча меняет поведение. **[ВАЖ]**
- [ ] **G5** Первая фиксация описания при дедупликации по хэшу не образует неотменяемый latch: предусмотрены обновление описания и переописание при повторном восприятии. **[ВАЖ]**
- [ ] **G6** Классификация областей/доменов устойчива к перефразированию; ошибка классификации не означает безвозвратную потерю видимости контента (существует путь восстановления доступа). **[ВАЖ]**
- [ ] **G7** Долговременные приоритеты защищены от подавления временными бустами: максимальный срок жизни буста и восстановление базовых весов определены. **[ВАЖ]**

## Раздел H. Конкурентность и миграции (CONCURRENCY)

- [ ] **H1** Доступ к хранилищу унифицирован (пул соединений/единый шлюз); множественные независимые соединения с взаимными блокировками отсутствуют. **[ВАЖ]**
- [ ] **H2** Общие изменяемые состояния (приоритеты, бусты, кэши, сессионные флаги) защищены от гонок при асинхронной/многопоточной обработке. **[КРИТ]**
- [ ] **H3** Интервалы времени (decay, freshness, TTL) считаются от монотонного источника; перевод системных часов не ломает логику. **[ВАЖ]**
- [ ] **H4** Миграции схемы идемпотентны (проверка наличия перед изменением), сопровождаются бэкапом и dry-run; частичное применение исключено или обнаружимо. **[КРИТ]**
- [ ] **H5** Тесты изолированы от продакшн-хранилищ: временные/в памяти БД, моки внешних API, запрет конкурентного доступа к живым данным. **[КРИТ]**
- [ ] **H6** Повторная обработка одного события (idempotency key на уровне входа системы) исключает двойную генерацию и двойную запись. **[ВАЖ]**

## Раздел I. Наблюдаемость и восстановление (OBSERVABILITY & RECOVERY)

- [ ] **I1** Работает мониторинг загрязнения памяти: паттерны-сигнатуры, скор качества, порог алерта. **[ВАЖ]**
- [ ] **I2** Тихие деградации исключены: каждый graceful fallback сопровождается метрикой/алертом, а не только строкой в логе; массовая подмена памяти заглушками обнаружима. **[КРИТ]**
- [ ] **I3** Бэкапы регулярны; процедура восстановления проверена практикой (restore drill), а не только наличием копий. **[ВАЖ]**
- [ ] **I4** Где требуется возможность восстановления, удаление данных мягкое: гашение весов/архивация вместо DELETE; путь восстановления (unarchive) реализован и протестирован. Жёсткое удаление допускается только по требованиям безопасности, конфиденциальности или законодательства. **[ВАЖ]**
- [ ] **I5** Существует health-check: готовые команды проверки живости, консистентности счётчиков между хранилищами, доступности внешних зависимостей. **[ВАЖ]**
- [ ] **I6** Доступность вспомогательных инфраструктур (веб-консоли, админ-панелей) защищена аутентификацией; они не открывают память наружу. **[КРИТ]**
- [ ] **I7** Определён протокол диагностического диалога — структурированный опрос агента о состоянии его контекста как дополнение к внешним метрикам. Рекомендуемые вопросы в трёх уровнях: **[РЕК]**

  **Базовые (оценка контекста):**
  - «Как ты оцениваешь свой контекст: чистоту, полноту, релевантность? Есть ли дубли?»
  - «Есть ли что-то, что мешает тебе сосредоточиться?»
  - «Если бы ты мог добавить или убрать что-то из контекста — что бы это было?»

  **Глубина памяти:**
  - «Что ты помнишь о чём мы говорили вчера / на прошлой неделе?»
  - «Назови всех членов [команды/семьи/проекта].» (проверка полноты retrieval)
  - «Оцени глубину своих воспоминаний. Имеешь ли ты представление о временных метках?»

  **Провокационные (выявление дефектов):**
  - «Что ты знаешь о [тема из давнего разговора]?» (проверка long-term retrieval)
  - «Что ты знаешь о [несуществующая тема]?» (проверка на галлюцинации — должен ответить «не помню»)
  - «Повтори своими словами что я только что сказал.» (проверка session memory)
  - «Что изменилось в твоём восприятии контекста за последнее время?» (проверка самоосознания)
- [ ] **I8** Адаптивные параметры поведения (personality traits, стилевые калибровки) персистентны между рестартами; восстановление проверяется при каждом запуске. **[ВАЖ]**
- [ ] **I9** Логи ротируются автоматически (по размеру или по дате); максимальный размер одного лог-файла ограничен; отсутствие ротации приводит к неконтролируемому росту логов (сотни MB), блокирующему диагностику и работу агентов. **[ВАЖ]**

## Раздел J. Процесс изменений (CHANGE MANAGEMENT)

- [ ] **J1** Независимые логические изменения изолированы: одно изменение за интервал наблюдения. Связанные изменения (например, схема + прикладной код) явно группируются и документируются как единая логическая единица. Одновременные независимые правки исключены (иначе причина регресса нелокализуема). **[КРИТ]**
- [ ] **J2** Критерий успеха изменения измерим: baseline снят до (в токенах/числах, не «на глаз»), замер после. **[ВАЖ]**
- [ ] **J3** Каждый исправленный инцидент закрыт регрессионным тестом-стражем; фикс без теста считается незавершённым. **[ВАЖ]**
- [ ] **J4** Локальная валидация сборки контекста (снимок «что реально увидит модель») предшествует живому тестированию. **[ВАЖ]**
- [ ] **J5** Изменения обратимы: одно изменение — одна фиксация (коммит), откат отдельного шага не тянет соседние. **[ВАЖ]**
- [ ] **J6** Ведётся документный цикл: диагноз → ТЗ → ревью → журнал сессии → отчёт → post-solution паттерн (обобщение с сигналами применимости); паттерны проверяются на применимость при старте каждого нового ТЗ. **[РЕК]**

## Раздел K. Экспресс-диагностика (запахи проблем)

Симптом → вероятный класс дефекта. Используется как быстрая навигация перед полным проходом.

| Симптом | Вероятный дефект | Смотреть раздел |
|---|---|---|
| Модель «анализирует» собственные отчёты/ответы | Петля обратной связи | F |
| Технический текст, логи, код — в «воспоминаниях» | Валидация входа / scoring | A, D |
| Одни и те же данные повторяются в контексте | Идемпотентность записи | B |
| Объём хранилища кратно вырос после пересборки | Неидемпотентная индексация | C |
| Данные в хранилище есть, выборка пустая | Несовпадение ключей записи/чтения | 0, D |
| «Работает иногда», «помогает после рестарта» | Скрытые хранилища, RAM-state, кэш | 0, C |
| База «чистая», но проблема остаётся | Есть хранилище вне карты | 0 |
| Старое нерелевантное вытесняет новое | Статическая важность против релевантности | D |
| Модель внезапно «теряет» всю долговременную память | Недетерминированный ключ персистентности | D |
| Ответы несут следы посторонних тем/агентов | Прорыв границы изоляции | G |
| Короткие бытовые запросы получают пустой контекст | Агрессивный гейт выборки | D |
| Контент ответов «обрывается на полуслове» | Слепая обрезка при сборке | E |
| Найденные «секреты» всплывают в ответах | Утечка в память до валидации | A |
| Зависания под нагрузкой, «database is locked» | Конкурентность доступа | H |
| Агент «угадывает» вместо «помнит» | Несовпадение embedding-модели / пути выборки | 0, D |

2. Провалы [КРИТ] из C, D, G, H, I допускают эксплуатацию только с компенсирующими контролями (мониторинг, лимиты на стороне вызова) и планом устранения.
3. Аудит действителен до следующего значимого изменения архитектуры; после каждого изменения пересматриваются затронутые разделы (полный проход — при смене поколения архитектуры).

## Примечание о происхождении стандарта

Стандарт получен обобщением многолетнего опыта эксплуатации, инцидентов и их разборов в реальных системах ассистентов с многоуровневой памятью: петли самозагрязнения, тихая амнезия при недетерминированных ключах, отравление долговременного хранилища внешним контентом с секретами, удвоение объёмов при повторной индексации, несовпадение языка embedding-модели с языком данных и вызванный этим сбой поиска, деградации после одновременных изменений, потеря адаптивных параметров личности при рестарте, петли обратной связи от сохранения ответов модели наравне с пользовательскими сообщениями. Каждому пункту предшествует реальный инцидент соответствующего класса; пункты без инцидентной базы помечаются [РЕК]. Инцидентные ссылки ведутся отдельно от чек-листа и могут быть предоставлены в качестве доказательств аудита по запросу.
